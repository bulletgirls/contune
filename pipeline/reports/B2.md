다음 카드에 알릴 것:
- 공개 이름: `Input`, `ActionKind`, 상수 `ActCreateFlowRun`·`ActDispatch`·`ActCreateRetry`·`ActSkipFire`(값은 카드대로 "create_flow_run" 등), `Action`, `Decide`, `NewFlowRun`, `FlowRunStatus`, `LatestFlowRun`, `IsDead`, 상태 상수 `FlowRunRunning`·`FlowRunSucceeded`·`FlowRunFailed`("RUNNING"/"SUCCEEDED"/"FAILED").
- **B4**: Decide 출력은 플로우 ID 순 → (발화 Action, 그다음 RUNNING 플로우 실행들을 시작 순으로, 스텝은 YAML 순의 진행 Action). 순서대로 적용하면 된다. `Input.Runs`는 최근 48시간 행 전부(모든 상태)를 넘길 것 — RUNNING 판정에 SUCCEEDED 행도 필요하다. 중복 exec_id는 Decide가 무시한다. `Loc` nil이면 UTC. `Scheduler.FlowRunning(flowID)`는 `LatestFlowRun` → 그 묶음의 `FlowRunStatus == FlowRunRunning`으로 만들면 skip_fire와 같은 기준이 된다(수동 실행 409). 재실행 행(B7)은 같은 flow_run_id로 CreateRuns만 하면 다음 tick에 Decide가 디스패치한다.
- `FlowRunStatus(f, runs)`의 runs는 플로우 실행 하나의 행(같은 flow_run_id)을 넘긴다. 다른 flow_id 행은 걸러내지만 flow_run_id로는 거르지 않는다.
- **B6**: 게이트는 decide.go `decideProgress`의 `StatusWaiting` 분기 주석 자리(`in.Gate`가 nil이 아니고 스텝에 gate가 있을 때)에 넣고, HELD 분기를 같은 switch에 더하면 된다. FlowRunStatus는 HELD를 RUNNING으로 본다.
- 정의가 바뀐 경우: 정의에서 사라진 스텝의 행은 무시, 행이 없는 스텝(실행 뒤 정의에 더해진 스텝)은 상태 계산에서 빼고 선행으로서는 충족으로 본다(플로우 실행이 영원히 RUNNING에 남아 다음 발화를 막지 않도록). 정의에서 사라진 플로우의 행은 Decide가 보지 않는다.
- "죽음에 막힌 WAITING"은 직접 선행이 죽었거나 직접 선행이 막힌 WAITING일 때다(강제 OK로 SUCCEEDED된 중간 스텝 뒤는 막히지 않음).
- 여러 cron 시각에 걸친 (Prev, Now]는 첫 시각으로 한 번 발화한다(ScheduledAt = 그 시각). 잘못된 cron은 조용히 발화하지 않는다(flowdef Validate가 잡아야 함, B1).
