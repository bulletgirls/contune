다음 카드에 알릴 것:
- 경로: POST /api/v1/runs/{exec_id}/force-ok `{"reason":"…"}`(선택, 빈 본문 가능, 깨진 JSON은 400) → 200 {"applied":true}; /rerun → 201 {"exec_id":"…"}; /kill → 202 {"requested":true}. 실패는 {"error":"…"}로 404(없는 실행) · 409(정의에 없는 플로우·스텝, 최신 attempt 아님 "최신 시도만 조작할 수 있습니다", 허용되지 않는 상태 "<조작>할 수 없는 상태입니다: <상태>").
- 검사 순서: 404 → 정의에 스텝 없음 409 → 최신 attempt 아님 409 → 상태 409. 최신 판정은 같은 flow_run·step 행 중 newerAttempt(attempt, scheduled_at, exec_id 순).
- 강제 OK reason은 "force-ok: <사유>", 사유가 비면 "force-ok". EndedAt은 비었을 때만 지금으로 채움. Forced=true.
- 재실행 행: 같은 flow_run·step·host, attempt+1, trigger "rerun", WAITING, scheduled_at 지금. 생성 이벤트 reason "rerun of <원래 exec_id>". 재실행이 실패하면 attempt ≤ retry.count일 때 자동 재시도가 그대로 붙고 trigger "rerun"을 이어 씀(B2 Decide).
- actor는 모두 "user:web(<원격 주소>)". 조작 뒤 s.kick(); kill은 s.wake()도 불러 롱폴링이 바로 받음.
- kill 요청은 호스트별 exec_id 집합(중복 요청은 한 번), 명령 조회 때 exec_id 순으로 꺼내고 지움. 매니저가 재시작하면 요청이 사라짐(알려진 한계). 에이전트가 명령을 받은 뒤 실행이 이미 끝났으면 에이전트가 모르는 exec_id로 무시해야 함(A6).
- kill 큐는 Scheduler 구조체(B4 소유 scheduler.go)를 고치지 않으려고 kill.go의 패키지 변수 sync.Map(*Scheduler → 큐)에 둠. Scheduler는 프로세스당 하나라 누수는 테스트에서만 생김.
- 감사 기록(AddAudit)은 남기지 않음(카드 범위 밖). run_events의 actor·reason으로 추적 가능.
