서버 트리·배치판·업무 패널은 화면 장식이 아니라 **규모를 다루는 방식**입니다. 3대·2개에서만 통하는 화면은 실제 업무 도구가 될 수 없으므로 개념과 같이 지킵니다. 대신 구현은 단순합니다: 경로 문자열 하나(그룹, 폴더)와 화면의 집계뿐이고 새 테이블은 `hosts.grp` 컬럼 하나입니다.

**15:00에 개념이 다 돌지 않으면** 넓이를 이 순서로 줄입니다: ① 서버 열지도를 이상 서버 목록만으로 ② CSV·접힌 스택 내보내기를 넓히기로 ③ 구간 끌어 고르기를 고정 구간 A·B로 ④ 그래도 늦으면 플레임 그래프 대신 상위 함수 표. **플로우 그래프, 프로파일 수집, 서버·배치판 트리는 줄이지 않습니다.** 줄인 뒤에도 세 흐름은 끝까지 이어져야 합니다.

## 6. 병렬 AI 세션 운영 규칙

자세한 규칙은 [04 §7](04-implementation-plan.md#7-카드-운영-규칙)에 있습니다. 요점은 다음과 같습니다.

1. **세션 4개 고정**(사람 1명당 2개). 세션은 카드 줄이고, **카드 1장 = 브랜치 1개**(`card/<id>-<이름>`)입니다. 카드를 시작할 때 카드 표기([상]/[하])대로 모델을 바꾸고, 다음 카드로 넘어갈 때 대화를 비웁니다.
2. **계약은 사람 1만 바꿉니다.** 세션은 멈추고 제안만 적습니다.
3. **테스트가 완료 기준입니다.** 카드의 "테스트 먼저" 표를 먼저 씁니다. 필수 등급은 미루지 않습니다(04 §9).
4. **카드가 끝날 때마다 병합합니다.** 조건은 최신 `main`으로 rebase, `go vet ./... && go test ./...` 통과, 쓰는 경로 안의 diff, 완료 보고입니다. 10:30·12:00·14:00·15:00은 병합 시각이 아니라 점검 시각입니다.
5. **먼저 끝난 세션은 대기열에서 카드를 가져갑니다.** [하] 카드는 어느 세션이든, [상] 카드는 사람 1의 세션만 가져갑니다.
6. **기다리는 시간에 검수합니다.** 사람 1은 [상] 카드를 직접 검수하고, [하] 카드의 diff도 병합 전에 훑습니다.
7. **기록을 남깁니다.** 세션 수, 카드 수, 커밋 수, 테스트 수, 코드 줄 수, 카드별 시작·완료 시각을 발표 자료에 씁니다.

## 10. 심사 예상 질문과 답변

| 질문 | 답변의 뼈대 |
|---|---|
| 실제 업무에 쓸 수 있나? | 운영에서 실제로 쓰는 핵심 기능(cron, 선후행, 원격 실행, 재시도, 서버·업무 관제)에 함수 단위 추적까지 실행 파일 하나에 있습니다. 설치는 매니저 1대와 서버마다 에이전트 1개, 폐쇄망에서 동작하고 방화벽은 매니저 포트 1개입니다. 코드가 사내에 있어 필요한 기능을 직접 붙입니다. |
| onTune의 top 기록으로도 찾을 수 있지 않나? | top 기록은 "체결 프로세스가 CPU를 다 썼다"까지입니다. 서버를 늘릴지 코드를 고칠지는 알 수 없습니다. 이음은 그 프로세스를 띄운 실행, 같은 시각의 접수·대기 건수와 응답시간, **CPU를 쓴 함수**까지 잇습니다. 몇 분 만에 지나간 폭주는 perf를 걸 때 이미 끝나 있지만, 이음은 띄운 순간부터 기록해 지나간 구간도 함수 단위로 봅니다. |
| 운영 서비스에 프로파일러를 붙이면 느려지지 않나? | 표본 방식(초당 49회), 켠 스텝만, 단명 프로세스 제외입니다. 실측(C `-O2` 시험 프로그램): 프로파일러 CPU는 코어 1개의 약 0.6%, 대상 프로그램 지연은 측정 오차 안이었습니다. 시연에서 부하 지표를 화면에 띄웁니다. |
| 우리 C 프로그램에서도 함수 이름이 나오나? | 실행 파일에 심볼이 남아 있으면 됩니다(strip 했다면 디버그 심볼 파일). 프레임 포인터 없이 `-O2`로 빌드한 C도 dwarf 방식으로 호출 경로를 복원하는 것을 확인했습니다. 시연 서비스도 같은 조건의 C 프로그램입니다. 자바는 `Profiler` 구현(JDK 내장 JFR)을 추가하면 같은 화면과 SQL을 씁니다. |
| 배치는 셸 스크립트인데? | 스크립트 자체가 아니라 스크립트가 띄운 C 프로세스를 추적합니다. 실행 ID를 환경변수로 넘기고 `/proc`에서 그 표식을 찾으므로, `setsid`나 `nohup`으로 빠져나가 장중 내내 도는 서비스도 같은 실행으로 잡습니다. |
| 장애는 온라인에서 나는데 스케줄러가 왜 같이 있어야 하나? | 체결 서비스를 띄우는 것도 새벽 준비 플로우입니다. 그 실행 ID가 서비스의 자원, 업무 지표, 함수 프로파일에 붙어 "어느 실행으로 뜬 서비스가 어디서 밀렸나"를 한 키로 봅니다. 정산 같은 배치는 체결 대기가 0건이 된 뒤 시작하도록 업무 지표를 조건으로 씁니다(리소스 게이트). |
| 잠금 대기로 느린 경우는? | CPU를 쓴 곳만 보이는 것이 한계입니다. 대기 시간 분석(off-CPU)은 root와 eBPF가 필요해 `Profiler` 확장으로 둡니다. |
| 상용 제품의 수많은 기능이 없지 않나? | 실제로 쓰는 기능 목록(기획서 1장 현황 수치)을 기준으로 답합니다. 쓰지 않는 기능의 비용을 내지 않는 것이 이 과제의 주장입니다. 검증판에서 뺀 고가용성, 휴일 캘린더, 권한은 인터페이스 자리가 있습니다. |
| 자체 개발은 유지보수 비용이 들지 않나? | 맞습니다. 그래서 줄어드는 비용(겹치는 상용 제품의 라이선스·유지보수, 제품별 관리 서버, 연동 개발, 조사 시간)과 늘어나는 비용(유지보수·기능 추가 인력, 전환·병행 운영, 저장 공간·보안 점검)을 함께 놓고, 금액은 병행 운영에서 실제 대체 범위가 정해진 뒤 계산합니다. Go 단일 언어, 외부 라이브러리 4개, 하루 만에 만든 코드 규모를 공개합니다. AI 코딩 도구로 고치는 비용이 낮다는 것은 오늘의 개발 기록이 보여줍니다. |
| 데이터 주권이 왜 중요한가? | 운영 데이터는 우리 업무에서 나왔지만 지금은 제품이 제공하는 화면과 보고서 범위 안에서만 봅니다. 이음은 실행 이력, 서버 지표, 배치·서비스 자원, 업무 지표, 함수 프로파일을 공개 스키마로 한 DB에 두어 SQL 한 번으로 묶고, 같은 데이터로 통계와 머신러닝을 돌립니다(시연 장면 6). |
| 머신러닝은 어디 있나? | **장애 위험 지수**입니다(05 §6). 과거 장애 기록(가져오기·직접 입력·자동 기록)을 라벨로, 같은 DB의 지표·로그·실행 이력을 특징으로 10분마다 로지스틱 회귀를 다시 학습해 "5분 안 장애 가능성"을 0~100으로 냅니다. 외부 라이브러리 없이 돌고, 사례가 모자라면 규칙 기반이라고 화면에 밝힙니다. 판단을 대신하지 않는 참고 지표이고, 학습 데이터는 CSV로 그대로 꺼내 사내 분석 팀이 다른 모델을 돌릴 수 있습니다. 사내 LLM은 `RiskModel`·`LLM` 인터페이스로 붙습니다. |
| 화면에서 작업을 만들면 아무 명령이나 돌릴 수 있지 않나? | 정의의 기준은 여전히 YAML 파일입니다. 편집기는 그 파일을 쓰는 도구이고, 새로 넣거나 바꾼 명령은 매니저 설정의 허용 목록(정규식)을 통과해야 저장됩니다. 저장·삭제는 감사 기록에 남고, 편집기는 설정으로 끕니다(기본 꺼짐). 자연어 초안은 저장하지 않고 사람이 검토해 저장합니다. 저장·삭제는 관리 역할만 할 수 있고(05 §16), 에이전트도 같은 허용 목록을 한 번 더 검사합니다. |
| Dagu, Prometheus 같은 오픈소스를 쓰면 되지 않나? | 그렇게도 묶을 수 있습니다. 다만 스케줄러, 모니터링, 함수 프로파일러가 각각 따로라 도구 사이마다 연동 지점이 생기고, 그 연동 코드와 저장소 3개는 우리가 관리합니다. 이음은 **실행, 처리 현황, 자원, 함수를 같은 키(exec_id)와 같은 시간축, 같은 DB로 묶는 데이터 모델**을 처음부터 설계해 연동 지점과 운영 구성을 줄이는 쪽을 택했습니다. |
| 업무마다 보고 싶은 지표가 다르지 않나? | 그래서 업무 지표 화면은 코드에 박지 않고 업무 패널 YAML로 정의합니다. 지표 이름, 집계, 단위, 임계치만 적으면 화면이 그립니다. 시연에서는 체결 패널 하나를 씁니다. |
| 업무 지표는 어떻게 모으나? | 업무 지표도 서버 지표와 같은 수집 체계(수집기 등록, 설정, 1초 수집, 전송)를 지납니다. 업무 프로세스가 에이전트에 지표를 직접 보내는 `push` 수집기가 있고(시연의 C 체결 서비스가 이 방식), 명령 결과를 읽는 `script` 수집기를 추가할 수 있습니다. |
| 시연 수치가 가짜 아닌가? | 체결 서비스는 합성 주문으로 부하를 만드는 시연용 C 프로그램이고, 함수 이름과 수치도 시연용입니다. 보여 드리는 것은 수치가 아니라 경로입니다: 스케줄러가 띄운 서비스를 실행 ID로 추적하고, perf로 함수 프로파일을 모아, 업무 지표와 같은 DB에 쌓고, 화면과 SQL로 꺼내는 과정이 실제로 동작합니다. 운영 서버는 perf를 쓸 수 있고, 실서버에서는 수집기 설정만 바꿉니다. |
| 2명이 하루에 정말 되나? | 완성 기준은 실행·연결·활용 세 흐름입니다. 사람 1명이 AI 세션 2개씩 모두 4개를 병렬로 돌립니다. 15:00에 개념 7개가 최소 형태로 한 바퀴 돌고, 이후에는 넓히기만 합니다. 함수 추적은 커널 기능(perf)을 쓰고 결과를 접는 코드만 만듭니다. 당일 세션 수와 커밋, 테스트 수를 공개합니다. |
| 몇 대까지 감당하나? | 화면은 그룹 트리와 열지도(칸 하나가 서버 하나)라 수백 대도 한 화면에 들어가고, 이상 있는 서버만 목록 위로 올라옵니다. 저장 용량이 먼저 한계에 닿습니다. 1초 수집 기준 수십 대는 검증판 구조로 충분하고, 그 이상은 `MetricStore`를 TSDB로 교체합니다(변경은 store 패키지에 한정). |
| 보안은? | 단방향 연결, 에이전트 토큰, 비root. 실행할 수 있는 명령은 검토된 YAML에 정의된 것뿐이고 화면에서 임의 명령을 입력할 수 없습니다. 프로파일 대상은 이음이 띄운 프로세스뿐이고, 접힌 스택에는 함수 이름만 있습니다. 상태 전이는 감사 기록으로 남습니다. 11-10에 화면 로그인과 역할 3개(조회·운영·관리), 호스트별 에이전트 토큰, 에이전트 쪽 명령 허용 목록(매니저가 뚫려도 서버는 정해진 명령만), TLS를 더했습니다(05 §16). 인증 판단은 조립부 두 곳에만 있어서 업무 코드는 거의 바뀌지 않았습니다. |
| AI는 어디에 썼나? | 제품이 아니라 **개발 방식**에 썼습니다. 설계 교차 검토, 계약 기반 병렬 구현, 테스트 검수. 하루 동안의 세션 수, 커밋, 테스트 수를 공개합니다. |
| 기대 효과는? | 세 가지입니다(기획서 7쪽). 복잡도와 관리 비용(실행 파일 1개·화면 1개·방화벽 포트 1개, 금액은 병행 운영에서 대체한 범위만큼 계산), 장애 조사(원인 추적 5단계 → 2단계, 수집된 구간은 재현 없이 CPU를 쓴 함수까지), 데이터 분석(운영 데이터 5종을 SQL로 엮어 처리량별 지연과 함수 비중 변화를 분석, 종료 시각 예측·이상 탐지는 확장). |
