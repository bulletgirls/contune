# 03. 단계별 구현 계획

> 원칙: **모든 마일스톤이 끝나는 시점에 데모가 가능해야 합니다.** 수평(레이어별) 분할이 아니라 수직(종단 간) 확장으로 진행합니다. 해커톤 일정에 맞춰 어느 마일스톤에서든 멈출 수 있게 합니다.

## 0. 데모에서 거꾸로 설계하기

**5분 데모 시나리오 (최종 목표 = M3 완료)**

| # | 장면 | 대체 대상 | 필요한 마일스톤 |
|---|---|---|---|
| 1 | 대시보드: 서버 2~3대의 1초 CPU, 메모리, 디스크와 업무 지표(주문 큐 적체)가 **같은 시간축**에 표시 | onTune + 업무모니터링 | M0, M1, M3 |
| 2 | `daily-settle` 플로우(fetch → settle → report)의 DAG와 cron 스케줄 | Control-M | M2 |
| 3 | settle이 같은 서버의 백업 잡 때문에 I/O가 막혀 **타임아웃**, 웹훅 알림 수신 | | M2 |
| 4 | 실패한 settle을 클릭하면 실행 구간으로 차트가 자동 확대되고, 잡 리소스 오버레이와 로그 tail이 함께 표시 | **통합만의 가치** | **M1** |

| 6 | (보너스) CPU 부하 중에는 잡이 **HELD**로 기다리다가 부하가 풀리면 자동 시작 | 통합만의 가치 | M2 |
| 7 | (보너스) 기존 Control-M 잡에 `contune exec --` 한 줄을 붙이면 바로 프로파일링 | 공존 전략 | M4 (필요하면 앞당김) |

**최소 데모 컷: M1**(장면 1, 4). **권장 컷: M3**(장면 1~6).

## 1. 마일스톤 개요

| M | 이름 | 끝나면 보여줄 수 있는 것 | 규모(1인 + AI 기준, 대략) |
|---|---|---|---|
| **M0** | Walking Skeleton | 에이전트 → 매니저 → SQLite → 브라우저 차트로 CPU 1초 그래프 | 1~2일 |
| **M1** | 잡 실행 + 프로파일링 | UI에서 잡을 수동 실행하면 잡 리소스가 호스트 차트에 겹쳐 표시되고, 이력/로그/peak가 기록됨 | 3~4일 |
| **M2** | 스케줄러 | cron 플로우, 선행 조건, 재시도, 타임아웃, 리소스 게이트, 운영자 조작, 웹훅 | 3~4일 |
| **M3** | 업무 지표 + AI | exec 프로브와 push로 업무 지표 수집, 근거 기반 AI 원인 분석, 소요 시간 이상 플래그 | 2~3일 |
| M4 | 공존 + 하드닝 | 래퍼 모드, 이벤트 스풀, TLS/권한, 보존 정책, cgroup, 캘린더 등 | 해커톤 이후 |

> 규모는 병렬 세션을 활용하면 줄어듭니다. 정확한 추정이 아니라 상대적 크기로 봐 주세요.

## 2. 마일스톤 상세

표기: **[상] 상위 모델**(동시성, OS, 상태 머신, 계약, 통합) / **[하] 하위 모델**(계약이 정해진 구현, 파서, 저장소, UI)

### M0. Walking Skeleton (세션 1개, [상])

가장 얇은 종단 간 흐름을 먼저 관통시킵니다. **이 단계에서는 병렬로 진행하지 않습니다.**

| WP | 내용 | 완료 기준 |
|---|---|---|
| 0.1 | 저장소 골격: `go.mod`, `cmd/contune` 서브커맨드(`manager`/`agent`/`dev`), Makefile(`test`/`build`/`lint`), CI(`go vet`, `go test`) | `make test` 통과 |
| 0.2 | `internal/model`(Sample 등) + API v1 DTO | |
| 0.3 | `CPUProbe`: `/proc/stat` 차분 계산(순수 파서 + `testdata/` 고정 파일) | 고정 파일 2개로 user/sys/iowait % 계산이 정확 |
| 0.4 | shipper → ingest → live 링 → SQLite `MetricStore`(5초 배치 flush) | |
| 0.5 | `GET /api/v1/series` + `index.html`(uPlot 1개, 2초 폴링) | |
| 0.6 | E2E 스모크: `dev` 모드를 띄우고 5초 뒤 series API에 샘플이 있는지 확인 | CI에서 통과 |

**완료 기준:** `contune dev`를 실행하면 브라우저에서 CPU 1초 차트가 움직이고, 두 번째 리눅스 머신의 에이전트가 붙으면 호스트를 선택할 수 있습니다.
**이 시점에 1차 동결:** `Probe`, `MetricStore`, API v1(metrics). 이후 병렬 세션은 이 계약에 맞춰 개발합니다.

### M1. 잡 실행 + 프로파일링 (병렬 시작)

| WP | 담당 | 내용 | 선행 | 완료 기준 (테스트) |
|---|---|---|---|---|
| 1.1 | [하] | Probe 확장: mem(`/proc/meminfo`), disk(`/proc/diskstats`), net(`/proc/net/dev`), loadavg | M0 | 고정 파일 기반 단위 테스트 |
| 1.2 | [상] | **Executor**: `Setpgid`, stdout/stderr를 **파일로 리다이렉트**하고 메모리에 tail 200줄, 타임아웃 시 SIGTERM → 유예 → `kill(-pgid, SIGKILL)`, exit code 수집 | M0 | `sh -c 'echo hi; exit 3'` → exit 3 + "hi" 캡처 / `sh -c 'sleep 60 & sleep 60'` 타임아웃 1초 → **손자까지** 종료 |
| 1.3 | [상] | **ProcessTracker (PGID)**: 1초마다 `/proc` 스캔으로 `job.cpu_pct`, `job.rss_mb`, `job.io_*` 수집, 종료 시 `Usage`(peak/합계) | 1.2 | `stress` 류 부하 프로세스로 peak CPU 50% 이상 기록 (linux build tag) |
| 1.4 | [하] | `StateStore` SQLite 구현 + **계약 테스트 스위트**(`storetest.Run(t, factory)`) | M0 | 메모리 구현과 SQLite 구현이 같은 스위트 통과 |
| 1.5 | [상] | `commands` 롱폴링 + `events` 엔드포인트 + **에이전트 측 exec_id 중복 제거** + 호스트 토큰 인증 | 1.2 | 같은 run 명령을 두 번 보내도 1회만 실행 / 토큰 없으면 401 |
| 1.6 | [하] | 플로우 YAML 로더와 검증: 필수 필드, **순환 탐지**, 미등록 호스트, 중복 스텝 ID | M0 | 잘못된 YAML 고정 파일마다 기대한 에러 |
| 1.7 | [하] | UI: 실행 이력 표, 수동 실행 버튼, **실행 상세**(로그 tail, 실행 구간 자동 확대, `job.*` 오버레이). 먼저 mock JSON으로 개발 | M0 | 화면 확인 |

**병렬 그룹:** `1.1 ∥ 1.4 ∥ 1.6 ∥ 1.7` ([하] 세션 4개) 과 `1.2 → 1.3`, `1.5` ([상] 세션)
**완료 기준:** UI에서 부하 테스트 잡을 실행하면 1초 단위 잡 CPU/RSS가 호스트 차트에 겹쳐 그려지고, 종료 후 이력에 peak, exit code, 로그 tail이 남습니다.

### M2. 스케줄러 (Control-M 최소 대체)

| WP | 담당 | 내용 | 완료 기준 (테스트) |
|---|---|---|---|
| 2.1 | [상] | **스케줄러 순수 코어** `Decide(now, flows, runs, snapshot) []Action` | 가짜 시계 + 표 기반 테스트: cron 발화, 선행 대기, 선행 실패 시 후행 WAITING 유지, 게이트 HELD/해제/`max_wait`, 재시도, 타임아웃, 이전 실행이 아직 돌 때 skip |
| 2.2 | [상] | 런너: tick 루프, Action을 StateStore와 commands 큐로 반영, **매니저 재기동 시 복구**(DISPATCHED/RUNNING이 응답 없으면 LOST), `on_missed` 정책 | 재기동 시나리오 통합 테스트 |
| 2.3 | [하] | 운영자 조작 API: `rerun`, `force-ok`, `hold`/`free`, `kill` + actor 감사 기록 | API 테스트 |
| 2.4 | [하] | `Notifier` webhook: FAILED, TIMEOUT, LOST, 장기 HELD, MISSED | 테스트 서버로 페이로드 확인 |
| 2.5 | [하] | UI: 플로우 목록, **mermaid DAG**(상태별 색), 조작 버튼 | 화면 확인 |

**완료 기준:** 데모 플로우가 cron으로 돌고, settle이 실패하면 report는 WAITING에 머물며 웹훅이 옵니다. force-ok 후 report가 실행됩니다. CPU 부하 중에는 HELD였다가 부하가 해소되면 시작합니다.

### M3. 업무 지표 + AI (해커톤 차별화)

| WP | 담당 | 내용 |
|---|---|---|
| 3.1 | [하] | **exec 프로브**: 주기적으로 스크립트를 실행하고 stdout의 `key=value` 줄을 `biz.*` 지표로 수집(타임아웃, 실패 무시). DB 미처리 건수나 큐 길이 같은 업무 지표를 기존 앱 수정 없이 수집 |
| 3.2 | [하] | `POST /api/v1/push`: 업무 앱이나 cron 스크립트가 curl 한 줄로 지표 전송 |
| 3.3 | [하] | UI: 대시보드에 업무 지표 패널 추가(같은 시간축) |
| 3.4 | [상] | **Evidence 수집기**(결정론적): 실행 구간의 호스트 지표 이상, 같은 호스트의 동시 실행 잡, 과거 N회 대비 소요 시간과 peak, 로그 에러 라인 |
| 3.5 | [하] | `Analyzer` LLM 어댑터 + 프롬프트 + 마스킹. LLM을 쓸 수 없으면 근거만 표시 |
| 3.6 | [하] | 소요 시간 이상 플래그(과거 평균 대비 배수, 단순 통계) + 알림 |
| 3.7 | [하] | **시드 데이터 생성기** `contune seed`: 7일치 이력과 지표(데모 차트와 기준선 비교용) |

**완료 기준:** §0 데모 시나리오 1~6 리허설 통과.

### M4. 공존 + 하드닝 (해커톤 이후 또는 여유 시)

- **래퍼 모드** `contune exec --flow X --step Y -- <cmd>`: Control-M과 공존. Executor와 Tracker를 재사용하므로 반나절 규모입니다. **피치에 필요하면 M3로 앞당깁니다.**
- 이벤트 로컬 스풀 + 재전송, 잡별 shim 프로세스(에이전트가 재시작해도 결과 회수)
- TLS, 사용자와 권한, 보존 기간과 다운샘플, 프로세스 Top-N, cgroup v2 Tracker, `run_as_user`(보안 협의 후), 휴일 캘린더, Parquet 내보내기, MySQL `StateStore`, TSDB `MetricStore`, 매니저 HA

## 3. 병렬 개발 운영 규칙 (멀티 AI 세션)

1. **M0는 세션 1개로 진행합니다.** 동작하는 골격과 계약이 생긴 다음에 병렬화합니다.
2. **WP 1개 = 패키지 1개 = PR 1개.** 담당 패키지 밖은 수정하지 않습니다. 계약을 바꿔야 하면 [상] 세션에 요청합니다.
3. **WP 프롬프트 템플릿:** ① 해당 인터페이스와 타입 ② 통과해야 할 테스트(또는 계약 테스트 스위트) ③ 금지 사항(새 의존성 금지, 다른 패키지 수정 금지) ④ 완료 기준.
4. **계약 테스트는 [상] 세션이 먼저 씁니다.** [하] 세션의 목표는 그 테스트를 통과시키는 것입니다.
5. **매일 main에 통합하고 E2E 스모크를 실행합니다.** 통합을 미루지 않습니다.
6. **[상] 배정 기준:** 동시성, OS 제어(Executor, Tracker), 상태 머신, 계약 변경, 통합. 나머지는 [하].

## 4. 테스트 전략

| 레벨 | 대상 | 방법 |
|---|---|---|
| 단위 | /proc 파서, exec 프로브 출력 파서, YAML 검증 | `testdata/` 고정 파일, 순수 함수 |
| 단위 | 스케줄러 코어 | 가짜 시계 + 표 기반(입력 상태 → 기대 Action) |
| 계약 | `MetricStore`, `StateStore` 구현 | 공용 스위트를 모든 구현에 실행(LSP 보장, DB 전환 시 재사용) |
| 통합 | Executor, Tracker | 실제 프로세스(`//go:build linux`) |
| E2E | `dev` 모드 | 잡 1개를 실행한 뒤 DB와 API 확인 |

**개발 환경 주의:** macOS에는 `/proc`이 없습니다. 실제 프로브는 `//go:build linux`로 분리하고 비리눅스 환경에서는 가짜 프로브를 씁니다. 통합 테스트는 리눅스 VM이나 컨테이너에서 실행합니다.

## 5. 데모 환경 주의

- **컨테이너 여러 개로 다중 호스트를 흉내 내면 안 됩니다.** 컨테이너 안의 `/proc/stat`과 `/proc/meminfo`는 **호스트 값**이라 3대가 똑같은 그래프를 그립니다. 실제 VM이나 개발 서버 2~3대를 확보하세요.
- **시드 데이터로 이력을 채웁니다.** 빈 차트는 설득력이 없고, AI 기준선 비교("평소 대비 2.4배")에도 이력이 필요합니다.
- **데모 녹화본을 백업해 둡니다.** 사내망이나 LLM 장애에 대비합니다.

## 6. 심사 예상 질문과 답변

| 질문 | 답변의 뼈대 |
|---|---|
| Dagu나 Beszel 같은 오픈소스를 쓰면 되지 않나? | 각각 스케줄러, 모니터링 단품입니다. **잡 실행, 리소스, 업무 지표를 같은 키(exec_id)와 같은 시간축으로 묶는 데이터 모델**이 핵심이고, 어느 단품에도 없습니다. |
| Control-M을 정말 대체할 수 있나? | 1단계는 **공존**입니다(래퍼 모드로 기존 잡 프로파일링). 신규 및 비핵심 배치부터 이관하고, HA, 캘린더, 권한은 로드맵에 있습니다. |
| 몇 대까지 감당하나? | 쓰기 성능보다 저장 용량이 먼저 한계에 닿습니다. 1초 수집 기준 수십 대는 MVP 구조로 충분하고, 그 이상은 `MetricStore`를 TSDB로 교체합니다(변경은 store 패키지에 한정). |
| 보안은? | 단방향 연결, 호스트 토큰, 리뷰된 YAML의 잡만 실행, 비root, 조작 감사 로그, LLM 전송 전 마스킹. |
| AI는 어디에 있나? | 장애 원인 분석과 소요 시간 이상 탐지. 근거는 코드가 수집하고 LLM은 요약만 하므로 환각을 통제합니다. |
| 업무 효율 효과는? | 장애 원인 분석이 "도구 3개 왕복"에서 "한 화면, 클릭 한 번"으로 줄어듭니다. **실측 수치**(예: 과거 장애 1건 재현 시간)를 넣으세요. 라이선스와 유지보수 비용 비교도 포함하세요. |

## 7. 열린 결정 사항

- [ ] 언어: **Go**로 확정할지

- [ ] "업무모니터링"의 실체와 **데모할 업무 지표 2~3개**
