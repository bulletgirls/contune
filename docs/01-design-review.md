# 01. 설계 점검: Gemini 조사 세션 리뷰

> 대상: "경량 모니터링 시스템 자체 개발 검토" 세션(PDF 20p). SRS, 유즈케이스, SAD, 상세 구현 계획까지 포함.
> 관점: **사내 AI 해커톤에서 빠르게 동작하는 1단계 제품**을 만들되, 확장할 수 있는 구조로.

> **이후 결정으로 바뀐 점 (2026-10-27).** 이 문서는 점검 당시의 기록이라 본문은 그대로 둡니다. 다음 항목은 결정이 바뀌었으니 02, 03 문서를 따르세요.
> - **AI 요소:** 해커톤의 초점은 제품 안의 AI 기능이 아니라 **AI로 개발하는 방식**과 업무 효율화입니다. 본문의 "AI 원인 요약"(§2 표, §4-5)은 범위에서 빠지고 확장 항목으로 내려갑니다.
> - **업무 모니터링의 실체(§4-6):** 지금은 사내 개발 **APM**(CS 프로그램)이 배치가 기동한 프로세스의 처리 현황(초당 주문 건수, 응답시간)을 봅니다. contune은 이 지표를 시스템 지표와 같은 통로로 받고, 검증판 수치는 시뮬레이터가 만듭니다.
> - **일정과 인원:** 해커톤은 **하루, 2명**이고 **코드는 당일 처음부터** 작성합니다(대회 규칙). 마일스톤 계획은 03 문서의 당일 계획으로 바뀌었습니다.
> - **방향:** 산출물은 **새 스케줄러의 개념 검증판**입니다. 기존 도구와 공존하는 래퍼나 단계적 이행 계획은 두지 않으므로, 본문 Q2의 "공존하다가 점진적으로 대체" 제안(래퍼 모드)은 채택하지 않습니다.
> - **창의성의 중심:** §0이 짚은 **데이터 주권**과 **함수 단위 추적**입니다. 운영 데이터를 공개 스키마로 우리 DB에 두고 SQL, CSV로 꺼내 분석·머신러닝에 쓰게 합니다(02 §6.1). 본문의 "잡별 리소스 프로파일링"은 자원 수준을 넘어, 스크립트가 띄운 C 서비스 프로세스가 CPU를 쓴 함수까지 실행 ID로 상시 기록하는 것으로 넓어졌습니다(02 §5.5, §5.6).
> - **시연 환경:** 실서버 대신 컨테이너로 시연합니다. 체결 업무 지표는 시연용 C 서비스가 실제로 처리하며 잰 값이고, 서버 자원과 게이트웨이 수치만 시뮬레이터입니다.

## 0. 결론

**방향은 맞지만 계획의 깊이를 잘못 잡았습니다.**

- 문제 정의(데이터 주권, 과한 기능, 업무 맞춤형 모니터링 부재)와 핵심 아이디어(**잡 실행 ID로 배치와 리소스 지표를 같은 키에 묶기**)는 아주 좋습니다. 이 프로젝트의 본질이니 그대로 가져가면 됩니다.
- 반면 구현 계획은 해커톤 MVP보다는 상용 제품 v1.0에 가깝습니다. 락프리 링버퍼, 자체 바이너리 프로토콜, LZ4, 공유 메모리, 월별 DB 롤링처럼 **데모 가치와 상관없는 저수준 최적화**에 상위 모델의 시간을 쓰도록 짜여 있습니다.
- 정작 필요한 것은 빠져 있습니다. 데모에는 **처음부터 끝까지 동작하는 흐름, AI 요소, 데모 시나리오**가 필요하고, 운영에는 **보안과 중복 실행 방지**가 필요합니다.
- Gemini의 한계는 질문할 때마다 "맞습니다"라고 하며 디테일만 늘렸다는 점입니다. 범위를 줄이자고 제안하거나 해커톤에서 무엇을 보여줘야 하는지 묻지 않았습니다. 그럴듯해 보이지만 실제로 틀린 내용도 섞여 있습니다(§3).

## 2. 질문별 점검

### Q1. onTune 같은 경량 모니터링을 자체 개발하는 방향 → **타당 (단, 범위 명시 필요)**

- 자체 개발 + SQLite + 웹 UI 방향은 맞습니다.
- 다만 onTune이 비싼 이유에는 **AIX, HP-UX, Windows 지원**과 **장기 보관**도 있습니다. `/proc` 기반 에이전트는 리눅스 전용입니다. 사내 대상 서버 중 유닉스와 윈도 비중을 확인하고 MVP 범위를 **"리눅스 배치/업무 서버"로 명시**하는 것이 좋습니다. 심사에서 반드시 나오는 질문입니다.
- 1~2초 수집은 기술적으로 쉽습니다. 어려운 부분은 **저장량**입니다(→ [02-mvp-architecture.md §6](02-mvp-architecture.md)).

### Q2. Control-M까지 통합 → **결론은 맞음, "95% 대체"는 과장**

결론("통합하되 내부는 느슨하게")은 맞습니다. 하지만 "핵심 5개 기능(크론, 캘린더, DAG, 로그, 재시도)으로 현업 배치 95% 대체"는 과장입니다. 실제 운영에서 매일 쓰는 다음 기능이 빠져 있습니다.

| 빠진 것 | 왜 중요한가 |
|---|---|
| **운영자 조작** (재실행, 강제 성공(Force OK), 보류/해제, 강제 종료) | 장애 시 DAG를 풀어주는 수단입니다. 이것이 없으면 실패 한 번에 후행 잡이 영원히 멈춥니다. |
| **실행 인스턴스 매칭** | "settle은 fetch 성공 후 실행"에서 *어느 날의* fetch인지 정의가 없습니다(Control-M은 업무일(ODAT)로 해결). |
| **놓친 스케줄 처리** | 02:00에 매니저가 내려가 있었다면 복구 후 돌릴지, 건너뛸지 정해야 합니다. |
| **매니저 SPOF** | UC-05는 "이미 도는 잡"만 다룹니다. 매니저가 죽으면 **새 잡은 아무것도 안 돕니다.** |
| **권한과 감사** | 누가 언제 어떤 잡을 수동 실행하거나 강제 성공시켰는지 기록해야 합니다(금융권 필수). |

**전략 제안:** 해커톤에서는 "Control-M 대체"보다 **"공존하다가 점진적으로 대체"**를 내세우는 편이 설득력이 큽니다. 기존 Control-M 잡의 커맨드 앞에 `contune exec --` 한 줄만 붙이면 기존 스케줄링은 그대로 두고 **잡별 리소스 프로파일링**을 바로 얻을 수 있습니다(래퍼 모드). 구현은 반나절이고 도입 장벽은 0입니다.

### Q3. SRS → **내용은 OK, 우선순위가 없음**

모든 요구사항이 같은 무게로 나열되어 있습니다. MVP 기준으로 다시 분류하면 다음과 같습니다.

| ID | 요구사항 | MVP 판정 | 비고 |
|---|---|---|---|
| MON-01 | 호스트 지표 초 단위 수집 | **Must** | CPU부터 시작해 mem, disk, net 순으로 확장 |
| MON-02 | 프로세스 핀포인트 추적 | **Must (축소)** | *잡 프로세스 그룹*만 추적합니다. 임의 데몬 감시는 나중에. |
| MON-03 | 커스텀 도메인 지표 | **Should (방식 변경)** | UDS/공유메모리 대신 **스크립트 실행(exec) 프로브 + HTTP push** |
| MON-04 | 인메모리 버퍼링 + 배치 전송 | **Must (단순화)** | 채널 + 2초 배치. 압축과 백필은 하지 않습니다. |
| SCH-01 | 잡/DAG 정의 | **Must (변경)** | YAML, **플로우(DAG) 단위 스케줄** (→ 02 문서 §7) |
| SCH-02 | 상태 머신 | **Must (보완)** | DISPATCHED, HELD, LOST 상태 추가 (→ 02 문서 §8) |
| SCH-03 | 리소스 인지형 스로틀링 | **Should** | 단순 임계치 + `max_wait`. 데모 효과가 큽니다. |
| SCH-04 | 실행 프로파일링 자동 태깅 | **Must** | 제품의 본질 |
| SCH-05 | stdout/stderr 캡처 | **Must (방식 변경)** | 파이프가 아니라 **파일로 리다이렉트**(§3-9) |
| SCH-06 | 영업일 캘린더 | **Later** | 데모에는 불필요합니다. |
| — | 운영자 조작(재실행, 강제 성공, 종료) | **Must (신규)** | |
| — | 에이전트 인증, 감사 로그 | **Must (신규)** | §4-1 |
| — | AI 원인 분석 | **Should (신규)** | AI 해커톤 차별화 요소 |

### Q5. 유즈케이스 → **UC-03이 데모의 핵심**

| UC | 판정 | 조정 |
|---|---|---|
| UC-01 리소스 인지형 실행 + 프로파일링 | **Must (축소)** | 프로파일링은 필수, 스로틀링은 단순 임계치. `setrlimit` 메모리 제한은 삭제(§3-2) |
| UC-02 업무 지표 + OS 지표 동시 관제 | **Should (축소)** | UDS/shm 대신 exec 프로브 + push. WebSocket 대신 폴링, 이후 SSE |
| **UC-03 원클릭 원인 분석** | **Must (데모 핵심)** | 여기에 **AI 원인 요약**을 붙이면 해커톤 스토리가 완성됩니다. |
| UC-04 무중단 ML 분석 | **설계만으로 확보** | 스키마만 열어두면 됩니다. 단, 장시간 읽기 시 주의(§3-5) |
| UC-05 단절 시 자율 생존 | **Later (부분)** | 잡 결과 이벤트의 재전송만 MVP에 포함합니다. 지표 백필과 100MB 스풀은 하지 않습니다. |

### Q6. 아키텍처 → **경계는 좋고, 구현 수단이 과함**

모듈 경계(수집 / 실행 / 전송 / 수신 / 캐시 / 스케줄러 / 저장)와 "인터페이스로만 대화한다"는 사상은 좋습니다. 다만 경계를 구현하는 **수단**이 대부분 과합니다.

| Gemini 제안 | 판정 | 대안 |
|---|---|---|
| C/C++ (문서 안에서도 C와 C++이 섞여 있음) | ✗ | **Go.** 단일 정적 바이너리, goroutine과 channel, `os/exec` + `Setpgid`, `net/http`, `embed`, 내장 테스트까지 모두 표준으로 제공됩니다. |
| 자체 바이너리 프로토콜(16B 헤더, LZ4, seq_no) | ✗ | **HTTP/JSON + `/api/v1` 버저닝.** 호스트당 초당 수십 개 지표 수준에서 JSON 파싱 비용은 의미가 없습니다. curl로 디버깅할 수 있다는 장점이 더 큽니다. |
| 영구 TCP + 우선순위 채널 2개 | △ | **엔드포인트를 분리**합니다: `metrics`(유실 허용) / `events`(재시도 + 멱등) / `commands`(롱폴링). HTTP만으로 우선순위 분리가 됩니다. |
| Lock-free 링버퍼 | ✗ | Go 채널, 또는 뮤텍스 + 슬라이스 링. 초당 수십 건에서 락 경합은 존재하지 않습니다. |
| 듀얼 SQLite 파일 | ○ | 유지하되 핵심은 파일 분리가 아니라 **인터페이스 분리**입니다. 확장 경로가 다르기 때문입니다(아래 마지막 행). |
| 월별 DB 파일 롤링 | △ | MVP에서는 생략합니다. 보존 기간 DELETE나 다운샘플은 나중에. 월 경계에 걸친 잡은 조인이 복잡해집니다. |
| UDS / 공유메모리 / 로그 테일 플러그인 | △ | 업무 앱을 수정해야 해서 침투적입니다. **exec 프로브**(스크립트 stdout `key=value`)와 **HTTP push**면 기존 앱 수정 없이 붙습니다. |
| WebSocket 스트리밍 | △ | MVP는 1~2초 폴링, 이후 SSE(서버 → 브라우저 단방향이면 충분) |
| `setrlimit` / cgroups 메모리 제한 | ✗ | RSS를 감시하다가 초과하면 kill(소프트 제한). cgroup v2는 지원되는 OS에서 이후에 도입합니다. |
| 호스트 지표는 고정 컬럼, 커스텀은 key/value로 혼용 | △ | **단일 series/samples 모델.** 새 프로브를 추가해도 스키마 변경이 없습니다(데이터 수준의 OCP). |
| `ODBCMetricSink`(지표를 MySQL/Tibero로) | ✗ | **상태는 RDBMS, 지표는 TSDB**(VictoriaMetrics 등)로 확장합니다. 1초 지표를 RDBMS에 넣는 방향은 규모가 커지면 무너집니다. |

### Q7. 상세 구현 계획 → **제시한 원칙과 계획이 서로 충돌**

1. **원칙 3(단순성) 위반.** 11개 WP 중 WP-02(락프리 링버퍼), WP-03(바이너리 직렬화), WP-08의 상당 부분(스풀러)은 MVP에 필요 없습니다. 그런데도 상위 모델 슬롯을 차지하고 있습니다.
2. **수평 분할이라 통합이 맨 마지막에 몰립니다.** 계획에는 "수직 관통(Vertical Slice)"이라고 써 있지만 실제로는 레이어별로 쪼개져 있습니다. 처음으로 처음부터 끝까지 동작하는 시점이 **Phase 3**이라 해커톤에서 가장 위험한 구조입니다. 반대로 **가장 얇은 종단 간 흐름(Walking Skeleton)을 첫날** 만들고 넓혀가야 합니다.
3. **Phase 0의 "인터페이스 동결"이 너무 이릅니다.** 동작하는 코드 없이 확정한 인터페이스는 대부분 틀립니다. 골격이 돈 다음에 거기서 추출해서 동결해야 합니다.
4. **빠진 작업:** 보안(인증), 설정과 배포, 잡 정의 로더와 검증, 알림, 운영자 조작, AI 기능, 데모 시나리오와 시드 데이터.
5. **병렬 세션 배정:** 상위 모델은 OS 제어(Executor, Tracker), 상태 머신, 계약, 통합에 집중시키고, 락프리 구조처럼 불필요한 난제에서 빼야 합니다(→ [03-roadmap.md §3](03-roadmap.md)).

## 3. 기술적 오류와 부정확한 부분

| # | Gemini 서술 | 문제 | 바로잡기 |
|---|---|---|---|
| 1 | `CREATE TABLE host_metrics (...) WITHOUT ROWID, STRICT;` (PK 없음) | SQLite에서 **WITHOUT ROWID 테이블은 PRIMARY KEY가 필수**입니다. 이 DDL은 실행하면 에러가 납니다. | `PRIMARY KEY (series_id, ts)` 명시 |
| 2 | `setrlimit`로 배치 잡 메모리 제한 | 현대 리눅스에서 `RLIMIT_RSS`는 **효과가 없습니다**. `RLIMIT_AS`는 가상 메모리 제한이라 JVM이나 Go처럼 주소 공간을 크게 예약하는 프로그램이 **정상 상황에서도 실패**합니다. | MVP는 RSS 감시 후 kill, 이후 cgroup `memory.max` |
| 3 | PGID로 "손자 프로세스까지" 추적하고 kill | 자식이 `setsid`, `nohup`, 데몬화로 **새 세션이나 그룹을 만들면 추적에서 빠집니다.** 리소스 집계도 누락됩니다. | MVP는 PGID로 충분합니다. 정확도가 필요하면 subreaper나 cgroup v2를 `ProcessTracker` 인터페이스 뒤에서 교체합니다. |
| 4 | 에이전트가 `/proc/[pid]/io`를 수집하고 `run_as_user`로 실행 | 다른 사용자 프로세스의 `io`는 같은 UID이거나 `CAP_SYS_PTRACE`가 있어야 읽을 수 있습니다. `run_as_user`는 **root 에이전트**가 필요합니다. 그러면 원격 명령 실행 에이전트가 root로 돌게 되고, 이는 보안 심의의 핵심 쟁점입니다. | MVP는 비root, 에이전트와 같은 사용자로 실행. run_as_user는 보안 정책을 협의한 뒤 도입 |
| 5 | "WAL이라 분석 쿼리가 쓰기를 1ms도 막지 않는다" | 장시간 읽기 트랜잭션은 **체크포인트를 막아 WAL 파일이 계속 커집니다.** WAL은 NFS 같은 **네트워크 파일시스템에서 동작하지 않습니다.** | 분석은 스냅샷(`VACUUM INTO`)이나 내보낸 파일을 대상으로 합니다. 라이브 DB는 같은 호스트에서 짧은 쿼리만 실행합니다. |
| 6 | `MetricSample.metric_key = "proc.1234.cpu"` | 이름에 PID를 넣으면 **카디널리티가 폭발**하고 "모든 프로세스" 같은 질의가 불가능합니다. | 이름은 고정(`job.cpu_pct`)하고 식별자는 별도 필드(`exec_id`)로 |
| 7 | 문서 간 불일치 | SAD는 C(`main.c`, `.h`)인데 구현 계획은 C++(`std::vector`, `virtual`)입니다. SRS 상태는 6개인데 UC-01과 WP-07에는 `THROTTLED`가 따로 등장합니다. 와이드 테이블 DDL과 내로우 `MetricSample` 구조체도 섞여 있습니다. | 02 문서에서 단일 정의로 정리 |
| 8 | `exec_id = '20261026_jobA_001'` | 일련번호를 발급하려면 동시성 조정이 필요하고, 재시작 시 충돌할 위험이 있습니다. | 시간순 정렬이 되는 ULID 같은 ID |
| 9 | `pipe()` + `dup2()`로 stdout/stderr 캡처 | **에이전트가 재시작되면 파이프가 끊기고**, 배치가 다음에 출력하는 순간 SIGPIPE로 죽습니다. 운영 배치를 모니터링 도구가 죽이는 셈입니다. | 자식의 stdout/stderr를 **파일로 직접 리다이렉트**하고 에이전트는 그 파일을 tail. 결과 회수까지 하려면 잡별 shim 프로세스를 둡니다(M4). |

## 4. 빠진 것

1. **보안.** 매니저가 에이전트에게 임의 명령을 보내는 구조 자체가 **원격 코드 실행 채널**입니다. 그런데 인증, 권한, 감사가 하나도 없습니다. 사내 보안 심의에서 가장 먼저 나올 질문이므로 MVP에도 최소한은 있어야 합니다(→ 02 문서 §9).
2. **정확히 한 번 실행.** 네트워크 재시도로 실행 명령이 두 번 도착하면 **정산 배치가 두 번 돕니다.** 에이전트 측 `exec_id` 중복 제거와 DISPATCHED/LOST 상태가 필요합니다.
3. **매니저 재기동 시 상태 정리.** RUNNING으로 남은 실행을 어떻게 확정할지 정의되어 있지 않습니다(UC-05는 에이전트 쪽만 다룸).
4. **실행 인스턴스 매칭과 운영자 조작.** Q2 참조.
5. **AI 요소.** ML은 `analytics/` 폴더의 부록 정도로만 있습니다. AI 해커톤이라면 "AI는 어디에 있나?"라는 질문에 데모로 답해야 합니다. UC-03에 **근거 기반 AI 원인 요약**을 붙이는 것이 가장 싸고 효과가 큽니다.
6. **"업무 모니터링"의 실체.** 사내에서 대체하려는 업무모니터링 시스템이 APM(트랜잭션 추적, 응답 시간)인지, 업무 KPI(처리 건수, 미처리 건수, 큐 적체)인지, 로그 키워드 감시인지 정의되어 있지 않습니다. MVP 범위와 데모할 업무 지표 2~3개를 정해야 합니다.
7. **데모 시나리오.** 무엇을 보여줄지가 정해져야 무엇을 만들지가 정해집니다(→ [03-roadmap.md §0](03-roadmap.md)).
