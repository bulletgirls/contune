Q2기존의 뭘 보완하는 건가요? 이 설계를 고른 이유

필요한 운영 기능과 데이터 연결을 함께 설계합니다.

이음은 실행·수집·저장을 공통 데이터 모델로 구성해, 별도 연동 지점과 운영 구성을 줄이는 방식을 선택했습니다. 보완 방법 네 가지를 같은 기준으로 비교했습니다.

방법기록을 잇는 방식추가 연동 개발관리할 구성 요소데이터 추출유지보수 책임
A. 지금 도구 + 연동도구마다 키가 달라 시각·서버 이름으로 맞춤도구 사이마다 개발. 제품별 API·로그 형식에 맞춤제품 3개와 각 관리 서버·저장소, 연동 모듈제품별 화면·보고서·API. 범위는 제품이 정함제품은 벤더, 연동 코드는 우리
B. 오픈소스 조합
스케줄러+관제+프로파일러		공통 키와 데이터 모델을 직접 설계도구 3개 사이 개발오픈소스 3개, 저장소 3개, 연동 코드저장소마다 다른 질의 방식우리. 도구별 업그레이드 대응 포함
C. 통합 관측 제품
상용 APM·관측 플랫폼		관측 데이터는 제품 안에서 연결. 배치 실행은 제품 밖기존 스케줄러와 연동. 폐쇄망 설치 조건 확인관측 제품, 기존 스케줄러벤더 저장소·API벤더. 기능 추가는 벤더 일정
D. 이음띄울 때 실행 번호를 붙여 처음부터 연결제품 안에서 처리. 별도 연동 지점 없음실행 파일 1개(매니저·에이전트 역할)와 DB공개 스키마. 읽기 전용 SQL·CSV우리. 코드 사내 보유

A~C로도 기록을 이을 수는 있습니다. 다만 도구 사이마다 연동 지점이 생기고, 그 연동 코드는 어느 경우든 우리가 관리합니다. 이음은 그 연결을 처음부터 제품 안에 둡니다.

번호는 띄우는 쪽이 붙이면 간단합니다

택배 송장번호처럼, 보낼 때 붙이면 이후 기록이 따라옵니다. 이음이 서비스를 띄우며 번호를 넘기면 자원·업무 지표·함수 기록이 별도 매칭 없이 같은 번호를 답니다.

선택 이유실행과 수집을 한 데이터 모델로 설계하면 연동 지점이 줄고, 기록은 처음부터 이어집니다.
